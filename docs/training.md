# Training Entry Point

## Supported Commands

The supported entry point is `python -m scripts.train`, which keeps the repository root on Python’s module path. The legacy invocation remains unchanged when no stateful controls are supplied:

```powershell
python -m scripts.train --config configs/deep3.toml --output-dir weights
```

It does not enable resume-state saving automatically.

The Phase 8.2 derived canonical candidate uses `configs/deep3_canonical.toml`. It differs from the original config only by batch size 64 instead of 192; all learning rates remain unscaled under `KEEP_EXISTING_UNSCALED`. This is a different optimization trajectory and needs separate owner approval before full execution. See [canonical-training-runbook.md](canonical-training-runbook.md).

## Stateful Canonical Controls

`scripts.train` provides four optional execution-level controls:

- `--resume-state <path>`: trusted local state for continuing the same run.
- `--save-training-state`: enables operational epoch-boundary state saving.
- `--require-empty-output-dir`: fresh-run collision guard.
- `--run-id <portable identifier>`: immutable canonical run identity.

Stateful mode requires a portable run ID and `--save-training-state`. A fresh stateful run with `--require-empty-output-dir` fails before dataset preparation if its output directory contains any entry. A resume requires the approved `training_state.pt` and `run_manifest.json` in the selected output directory and rejects unexpected artifacts, remote locations, metadata mismatch, and completed state.

The run manifest contains portable run identity, config hash, dataset identity, hyperparameters, device/runtime versions, expected artifact names, resume capability, and publication policy. It does not record tokens, environment variables, private paths, cache paths, email, or process command lines.

## Epoch-Boundary Resume Semantics

The resume state is a separate operational artifact; it does not replace best-fold or final checkpoints. It is atomically written as `training_state.pt` through a unique temporary file in the same output directory and replacement.

After each successful epoch, the training flow performs training, validation, metric calculation, best-model decision, history update, and `scheduler.step()` before recording a recoverable `RUNNING` state. At a completed fold, it writes `FOLD_COMPLETE` with the next fold and epoch 1. After the final raw-model save it writes `COMPLETED`, which normal resume rejects.

The state includes `model_state_dict`, `ema_state_dict`, `optimizer_state_dict`, `scheduler_state_dict`, `grad_scaler_state_dict`, `python_rng_state`, `numpy_rng_state`, `torch_cpu_rng_state`, `torch_cuda_rng_states`, histories, accuracies, best accuracy, and train/validation-index hashes. On resume, immutable metadata and index hashes validate before state is applied; model, EMA, criterion, optimizer, scheduler, and GradScaler are rebuilt; then state dictionaries, histories, best accuracy, and RNG are restored. CPU and CUDA RNG byte states are returned to CPU before their respective PyTorch restore APIs, because loading a trusted state with CUDA map location may otherwise migrate those bytes.

A state may be loaded only from a trusted local file generated by this project. Operators must not load a downloaded or untrusted state file. The mechanism continues the same run; it does not claim bit-for-bit from-scratch reproducibility. It does not add global initial seeding or change the configured cuDNN behavior.

## Preserved Training Behavior

The script continues to reuse the established dataset preparation, transforms, CMT classifier, criterion selection, optimizer, scheduler, AMP GradScaler, EMA, train/validation loops, metrics, best EMA checkpoint policy, final raw-model policy, and fine-tuning condition `epoch > epochs - fine_tuning_epochs`. Batch size changes only in the separate derived config; epochs, folds, loss selection, optimizer/scheduler semantics, transforms, model architecture, and evaluation remain unchanged.

The existing `scripts/evaluate.py` remains independent of resume state and still requires best-fold checkpoints in fold order. No weights, checkpoints, dataset files, or logs are committed by this repository workflow.
